QEMU 版本进化史：从 TCG 翻译器到三平台硬件加速生态

2026-10-17 ·约 10 分钟 ·掌柜 老郭

QEMU 用二十多年迭代把自己从一个跨架构模拟器变成了覆盖 Linux/macOS/Windows 三平台的虚拟化基础设施，这条演进路线藏着开源项目如何找到"第二曲线"的经典样本。

我现在正用 QEMU 在 x86_64 的笔记本上跑一个 ARM64 的 Ubuntu 24.04 虚拟机，编译一个 C++ 项目。性能不算惊艳——大概是物理 ARM64 机器的 80%——但这件事本身就值得停下来想一想：十年前你敢在一台普通 PC 上流畅模拟另一套架构的整个操作系统吗？更别说它还能反过来，在同一台机器上用接近原生的速度跑 x86 虚拟机，而且三个操作系统平台通吃。

这就是 QEMU 当前的状态——它的官网上写得很清楚：一个同时扮演"跨架构模拟器"和"硬件加速器"双重角色的开源项目，全球绝大多数云服务商的虚拟化底层都绕不开它。但走到这一步，它并不是一开始就想清楚了的。

来路：一个翻译器怎么变成基础设施

QEMU 诞生于 2003 年，作者是 Fabrice Bellard——就是那个写了 FFmpeg 的人。最初的定位非常朴素：一个轻量级的跨架构模拟器，用 TCG（Tiny Code Generator）把一种架构的指令逐条翻译成另一种架构能执行的指令。比如你在 x86 上跑 ARM 程序，TCG 就把每条 ARM 指令翻译成 x86 指令，动态生成、即时执行。

这个设计让 QEMU 立刻拥有了一个商业虚拟化软件根本做不到的能力——真正的跨架构。VMware、VirtualBox、Hyper-V 都只能在架构相同的时候加速，跨架构就只能降级到纯软件模拟，慢到不能用。但 QEMU 不一样，TCG 从第一天就是为"架构 A 模拟架构 B"设计的。你可以在 x86 上跑 ARM、PPC、SPARC、MIPS……甚至反过来在 ARM 上跑 x86。这种灵活性让 QEMU 在嵌入式开发、逆向工程、跨架构编译这些小众领域迅速站稳了脚跟。

但纯 TCG 模式有一个致命问题：性能。每条指令都要翻译一次（虽然有缓存），计算密集型工作负载下性能只能到物理机的 5%~10%。能用来跑个轻量系统试试，但真要干活就不行。

转折点在 2007 年。那一年 KVM（Kernel-based Virtual Machine）合并进了 Linux 主线内核。KVM 本身不是模拟器——它是 Linux 内核提供的一个硬件虚拟化接口，把 Linux 内核变成了一个虚拟机监控器。但 KVM 不做设备模拟、不做指令翻译，它需要一个用户态程序来配合。QEMU 恰好就是那个最合适的搭档。

QEMU 和 KVM 结合之后，角色发生了根本性变化。它不再需要自己翻译 CPU 指令了——当宿主机和虚拟机架构相同时，QEMU 可以通过 /dev/kvm 设备文件把 CPU 指令直接丢给硬件执行，自己只负责设备模拟和状态协调。这就是 KVM 模式下性能接近原生的根本原因：Guest 的普通算术指令、内存访问指令完全不经过 QEMU，直接跑在物理核心上。只有涉及 I/O 和特权操作时才需要 QEMU 介入。KVM 加速器的调优参数、设备配置和权限验证细节，在qemu文档里都有详细说明。

这个变化让 QEMU 从一个"能用的模拟器"变成了"好用的虚拟机管理程序"。但团队没有停在这里。接下来十年里，他们一直在啃另一块硬骨头：半虚拟化设备。

纯模拟设备（比如传统的 RTL8139 网卡、Cirrus VGA 显卡）性能很差，因为 Guest OS 要通过 I/O 端口和 MMIO 寄存器跟模拟设备通信，每次中断都要 VMEXIT。解决方案是 VirtIO——一套半虚拟化设备标准。Guest OS 安装 VirtIO 驱动后，和 QEMU 之间通过共享内存队列通信，避免了大部分 VMEXIT。VirtIO 系列从网卡（virtio-net）开始，逐步扩展到磁盘（virtio-blk）、显卡（virtio-gpu）、串口（virtio-serial）、输入设备（virtio-tablet）……到今天几乎覆盖了所有常见设备类型。这套标准后来被 OASIS 国际组织标准化，云原生领域的 Firecracker、Cloud Hypervisor 都直接复用 VirtIO 设备。

三平台加速的补全

KVM 搞定了 Linux，但 QEMU 的用户不止 Linux 开发者。macOS 上有大量 iOS/macOS 开发者需要跨架构测试，Windows 上也有不少人需要跑 Linux 虚拟机，三个平台的安装包从官方下载拿就行。

macOS 的硬件虚拟化框架叫 Hypervisor.framework（HVF），从 2017 年开始 QEMU 集成了 HVF 加速支持。Apple Silicon 推出后，HVF 的性能表现甚至超过了 KVM 在某些场景下的表现——因为 Apple Silicon 的虚拟化扩展设计得更干净，VMEXIT 延迟更低。现在在 Apple Silicon Mac 上用 QEMU 跑 ARM64 Linux，性能几乎和物理机没区别。

Windows 的路稍微曲折一点。先是 Intel 的 HAXM 驱动，但 Intel 后来停止维护了。QEMU 转向 Windows 官方的 WHPX（Windows Hypervisor Platform），这是 Windows 1803 版本之后提供的硬件虚拟化接口。WHPX 的生态比 KVM 弱一些——嵌套虚拟化、某些 CPU 特性透传还不如 KVM 成熟，但基本够用了。

到这一步，QEMU 完成了 Linux（KVM）、macOS（HVF）、Windows（WHPX）三平台的硬件加速覆盖。加上 TCG 跨架构模拟始终在线，QEMU 成了唯一能在三个主流操作系统上、同时支持"同架构加速"和"跨架构模拟"的开源虚拟化工具。

从迭代节奏看团队的优先级

写完这些版本节点，回头看 QEMU 二十多年的迭代节奏，有两个非常清晰的规律。

一直在死磕的：硬件加速适配和 VirtIO 设备生态。几乎每个大版本更新都能看到新的硬件加速特性（更细粒度的 CPU 特性透传、嵌套虚拟化、大页内存支持）和新的 VirtIO 设备（最近几个版本在补 virtio-snd 声卡、virtio-iommu、virtio-mem 动态内存）。这两块直接决定性能上限，是 QEMU 的核心竞争力。

一直不怎么管的：上层 GUI 和企业级管理。QEMU 自己只提供命令行和一个最基础的 GTK/Cocoa 窗口。图形化管理界面 virt-manager 是 Red Hat 的另一个项目（依赖 libvirt），企业级的热迁移、集群管理、计费系统都是 libvirt 或 OpenStack 层面的事。QEMU 团队把自己的边界划得很清楚：我只做模拟器和设备管理，上层的事交给别人。

这个边界感很值得玩味。很多开源项目容易被用户需求拉着走，今天加个 GUI、明天加个集群管理，最后把自己做成一个四不像。QEMU 始终守住了底层基础设施的定位——不管上层怎么变，我保证指令翻译和设备模拟这两件事做好。这个定位让它在云原生时代反而成了香饽饽：Firecracker、Cloud Hypervisor、Google 的 gVisor……各种轻量级虚拟化方案底层都在用 QEMU 的设备模型或 VirtIO 标准。

预判：下一步大概率的走向

从这二十多年的迭代规律推，我觉得 QEMU 接下来的走向大概有三条线。

第一，ARM64 加速会继续深化。Apple Silicon 的成功让整个行业都在往 ARM64 迁移，QEMU 在 ARM64 上的 HVF 加速已经很快了，但跨架构模拟（x86 → ARM64）的 TCG 性能还有很大提升空间。ARM64 的 SVE/SVE2 指令集透传、嵌套虚拟化在 ARM 上的完善，都是可以预见的方向。

第二，VirtIO 设备会继续扩展。virtio-snd 声卡、virtio-iommu、virtio-mem 动态内存这些还在补全的设备会逐步稳定下来。随着 VirtIO 被更多轻量级虚拟化方案采用，QEMU 作为 VirtIO 设备的"官方参考实现"，会持续投入。

第三，跨架构模拟的性能天花板会被继续往上推。TCG 的多线程翻译（thread=multi 参数）已经让跨架构模拟性能提升了一大截，但距离"同架构加速"还有数量级的差距。会不会引入类似 Rosetta 2 的二进制翻译加速技术？这是我最期待的方向，但官方没提过，纯猜测。

写了这么多，回头看看开头那个场景：x86 笔记本跑 ARM64 Ubuntu、性能能到物理机的 80%。这件事之所以能实现，本质上是 QEMU 二十多年迭代的一个缩影——从一个简单的翻译器，逐步长出硬件加速的翅膀，再把 VirtIO 生态搭起来，最后在三个平台上都站稳了脚跟。这条路不是一开始就设计好的，是每一步都把当下的事做到极致，自然长出了下一条路。

如果你也想试试看，装起来就是几条命令的事。真正让它发挥威力的地方在那些深度用法里——调 KVM 加速器参数、配 VirtIO 设备、用 qemu-img 管理 qcow2 磁盘、甚至用 virgl 在虚拟机里跑 3D 图形加速。
