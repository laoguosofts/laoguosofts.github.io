用 Prisma 两周，我终于把写 SQL 的坏毛病戒掉了

2026-10-17 ·约 9 分钟 ·掌柜 老郭

从 Sequelize 和原生 SQL 切到 Prisma 的第一手体验——声明式 Schema 是真香，但迁移那条路真的得想清楚再上。

上个月接了个小项目，后端用 Node 加 PostgreSQL，之前我一直手撸 SQL 或者套个 Sequelize，写查询的时候总觉得别扭——SQL 字符串里拼参数怕注入，Sequelize 那套链式调用又感觉在跟 ORM 斗智斗勇。朋友强推我试试 Prisma——它的官网上介绍这是个为 TypeScript 而生的 ORM 工具——说「你会写类型，就会用 Prisma」。抱着半信半疑的心态装了，没想到两周下来真的回不去了。

第一眼：Schema 是真的香

安装倒没什么特别的——Prisma下载页上也有详细步骤参考——npm install prisma @prisma/client，然后跑 npx prisma init 就生成了 prisma/schema.prisma 和 .env。真正让我眼前一亮的是第一次写 Schema 的感觉——之前用 Sequelize 写 model 要在 JavaScript 对象里定义字段，类型、默认值、关系全塞在对象字面量里，写久了眼花缭乱。Prisma 用的是一套声明式语言，字段类型、属性、关系都一目了然：

model User {
  id        Int      @id @default(autoincrement())
  email     String   @unique
  name      String?
  role      Role     @default(USER)
  posts     Post[]
  createdAt DateTime @default(now())
}

model Post {
  id        Int      @id @default(autoincrement())
  title     String
  content   String
  author    User     @relation(fields: [authorId], references: [id])
  authorId  Int
}

这种写法的好处是——TypeScript 类型推断直接给你。role 字段是 enum，TypeScript 会自动推成 'USER' | 'ADMIN' | 'MODERATOR'，拼写错误编译期就炸了。之前用 Sequelize 写查询条件的时候经常把字段名拼错，运行时才报错，现在编辑器直接红线划出来。说实话，光是这个类型安全就值了切换成本。

迁移那条路：别纠结，选一种走到黑

踩的第一个坑是迁移。Prisma 给了两条路：migrate dev 和 db push。前者会生成 SQL 迁移文件存进 Git，每次改 Schema 都留历史记录；后者直接把 Schema 同步到数据库，不留痕。我一开始图方便，原型阶段全用 db push，快速迭代确实爽，改一下 Schema 推一下就行，不用操心迁移文件名起什么。

但项目要进测试环境的时候傻了——prisma migrate deploy 找不到任何迁移文件，db push 在生产环境是明确禁止的（文档里说会静默执行破坏性变更，比如删列改类型都不提示）。最后只能重置了一次测试库，跑了 migrate dev 正式起步。这个教训挺实在的：原型阶段用 db push 没问题，但只要你觉得这个项目能活过两周，尽早切到 migrate dev。

用了 migrate dev 之后发现它有个很贴心的功能——破坏性变更检测。比如我把一个 age Int 改成了 age String，它会弹窗警告说这个变更会丢数据，问我要不要继续。之前用原生 SQL 直接跑 ALTER TABLE users ALTER COLUMN age TYPE varchar，万一有脏数据直接报错崩库，现在至少有个预警。

原始 SQL：兜底方案用着真香，但别养成依赖

Prisma Client 的查询 API 覆盖了绝大多数场景，findMany、create、update、关系嵌套查询都好用。但有一天要做个报表，按用户按月聚合排名，要用 ROW_NUMBER() OVER PARTITION BY 窗口函数——Prisma Client 不支持窗口函数，直接回退到了 $queryRaw。

一开始还担心 SQL 注入，结果 Prisma 用模板字符串做参数绑定：

const rankings = await prisma.$queryRaw`
  SELECT
    user_id,
    DATE_TRUNC('month', created_at) as month,
    ROW_NUMBER() OVER (PARTITION BY DATE_TRUNC('month', created_at) ORDER BY total DESC) as rank
  FROM user_stats
`

模板字符串里的变量 Prisma 会自动处理绑定，不用自己拼 ? 占位符或者写 $1, $2。唯一要注意的是别用 $queryRawUnsafe，Prisma文档说这个接口存在就是给那种 100% 确定输入安全的场景用的，平时根本不该碰。

不过有个小遗憾：$queryRaw 返回的是原始行对象，没有类型推断也没有关系处理，复杂查询写起来还是挺费劲的。能用 Prisma Client 就尽量用，把 raw 当成真正的兜底，别反过来养成依赖。

枚举和 JSON 字段：灵活又安全

Schema 里的 enum 声明也比之前舒服。比如定义个用户角色，Prisma 会自动在 PostgreSQL 里创建原生枚举类型，字段直接映射，TypeScript 那边也同步拿到字面量联合类型。我之前用 Sequelize 是在 model 里写 enum: ['USER', 'ADMIN']，数据库里存的是字符串，没有原生约束，全靠应用层校验。

JSON 字段这个功能我倒是用得比较克制。Prisma 的 Json 类型可以直接存对象，客户端里读出来就是正常的 JavaScript 对象，不用 JSON.parse。但我只在两种场景用它：用户偏好设置和审计日志。之前有项目把整个动态表单的数据塞 JSON 字段里，后来要按表单里的某个字段筛选就惨了，MySQL 的 JSON 查询体验比 PostgreSQL 差远了。能结构化就结构化，JSON 只是补位的。

谁适合用 Prisma？

如果你用 TypeScript、用关系型数据库（PostgreSQL、MySQL、SQLite 都行），那 Prisma 值得试。它最吸引我的点是「声明式 + 类型安全」——Schema 就是真相源，改了 Schema 跑一下 prisma generate 客户端自动更新，编辑器里自动补全查询方法和字段名，这体验比手写 SQL 或者跟 ORM 斗智斗勇强太多了。

但有几点要想清楚再上：SQLite 不支持 JSON 字段和枚举原生映射，MongoDB 用 Prisma 的话迁移功能是阉割版（没有真正的 schema 迁移）；如果你团队里有人对 Prisma 不熟悉，第一次上手会觉得 Schema Language 有点陌生，但也就两三天的事；还有迁移那条路别纠结，选 migrate dev 就坚持到底，原型阶段图省事用 db push 也行，但记得提前切，别等生产环境炸了再收拾。

说实话两周下来我还没碰到让我想换回原生 SQL 的场景。之前总觉得「手写 SQL 才是真本事」，现在觉得能让我少写点样板代码、少出点低级错的工具都是好工具。Prisma 没那么神，但在它擅长的领域——声明式 Schema 建模 + 类型安全查询 + 版本化迁移——真的做得很扎实。怕有些同学访问 GitHub 不方便，这套 Prisma 的资料我在GitHub、Gitee和GitCode上都各存了一份。
