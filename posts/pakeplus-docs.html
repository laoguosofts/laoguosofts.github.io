把 PakePlus 翻了个底朝天——六个你可能没注意到的冷门玩法

2026-10-17 ·约 8 分钟 ·掌柜 老郭

PakePlus 不只是个网页套壳工具。窗口尺寸锁死、Token 分层存储、Win7 绿色版旁路、双打包路径混用，这些藏得真深的细节能省你不少麻烦。

你以为 PakePlus官网 就是个"网页转桌面 App"的壳工具？打开客户端、填个 URL、点发布，完事。我之前也是这么想的——直到最近把它翻了个底朝天，才发现它藏着不少官方文档没怎么宣传、但真能用上的东西。

窗口模式里的「隐形开关」

配置页面里的窗口模式，很多人看一眼就跳过了——默认选「桌面端」，窗口可以自由拖拽缩放，够用就行。但我要讲的不是五个预设模式本身，而是两个跟它绑定的、几乎没人注意到的细节。

第一个是自定义模式的真正用途。PakePlus文档里写了可以手动填宽高，但没说什么时候该用。我做了个 480×320 的小工具，默认窗口模式选了桌面端，用户打开后窗口乱调，控件全挤在一起成一团。改成自定义锁死尺寸后，每次打开就是我想要的样子，用户还以为这是软件本来的设计。除了工具类应用，模拟 Apple Watch、折叠屏这类非预设尺寸的设备时，自定义模式也是唯一的路子——iPhone 和 Android 那两个预设是固定值，改不了。

第二个是「窗口保持」这个小复选框的副作用。配置完点预览，调了一下窗口大小，发现下次打开配置页，预览窗口记住了我调过的尺寸。再看配置面板底部，有个不起眼的「窗口保持」勾选项——勾上之后，用户每次调整完窗口，下次启动就会用他上次调过的尺寸，直接覆盖掉你在配置里写的默认值。这对普通桌面应用是好事，但如果你做的是固定尺寸的工具，千万别勾——勾了就等于把尺寸控制权完全交给用户。

顺带说个容易踩的坑：窗口模式只管桌面端 APP，跟移动端打包页面（右上角那个手机图标）完全是两套独立配置。很多人以为在配置页选了 iPhone 模式，云端打包出的移动端也会按这个尺寸渲染——不是的，移动端有自己单独的配置面板，包名、图标、渲染尺寸全在那边。两个页面的配置互不影响，别指望一个项目同时完美适配桌面和手机，分两次打包更稳。

Token 不是随便存的——它有分层

第一次用 PakePlus，让填 GitHub Token，存完就没多想了。后来在别人那台 Windows 机器上翻配置，发现 Token 不在配置文件里——去 Windows Credential Manager 里才找到。再去 Mac 上看，存进了系统钥匙串。原来 PakePlus 根据操作系统自动选存储后端：Windows 走 Credential Manager，macOS 走钥匙串，Linux 优先 Secret Service API（GNOME Keyring 或 KWallet），都不行才退回本地配置文件。

这听起来是个技术实现细节，但对你来说有实际意义。比如公司里有人帮你代操作 PakePlus，你不想给他看 Token——退出登录就行，Token 从系统凭据里清掉，本地配置文件里也不留。反过来，如果你在自己电脑上想备份项目配置，放心去拷 %APPDATA%/PakePlus/ 里的文件——Token 不在里面，拷走也泄露不了。

还有一点值得注意：打包产物里完全不包含你的 GitHub Token。Token 只在 PakePlus 客户端里用，就是推送配置到 fork 仓库、触发 GitHub Actions 那几步。打包出来的 APP 里只有网站 dist 内容，不带任何凭据。所以把打包好的 EXE 发给别人用，完全不用担心你的 GitHub 权限被拿到。

绿色版的 Win7 旁路

绿色版 vs 安装版的对比文档大家大概扫过一眼——绿色版不写注册表、解压即用、删目录就卸载。但文档里有一句话我翻了三遍才注意到：绿色版直接运行，绕过安装器的所有版本检查。

这句话单独看没什么，但放到 Win7 语境里就值钱了。安装版的 NSIS 安装程序在 Win7 上经常弹兼容性错误，装不上。绿色版不经过安装器那一套，双击 EXE 直接跑——前提是 Win7 机器上有 WebView2 Runtime（现在 Win10/11 自带，Win7 得手动装一下，PakePlus 会弹窗提示）。公司里还有老 Win7 机器的同事，试过这个旁路，能跑起来。

不过绿色版的局限也别指望绕过——不能关联文件类型、没有开机自启动、不能自动更新，这些是分发形态本身的限制，跟 PakePlus 没关系。想要这些功能还是得上安装版，下载直接拿就行。

云端和本地可以混用，而且应该混用

我之前以为两条路径是二选一的——要么全用云端，要么全用本地。其实项目配置和 dist 文件是共享的，两条路径可以串起来用，效果比单走一条好太多。

开发期用本地打包。改个配置、调个窗口尺寸、换个图标，30 秒出一个包直接开预览，比等 GitHub Actions 跑 3 分钟快得不是一点半点。这时候不用纠结 Token 权限、不用管 GitHub 网络能不能访问，纯本地闭环。

确认没问题之后，切云端打包出正式版。点一下发布，GitHub Actions 自动并行编译 Win、macOS、Linux 三个平台（加移动端就是五六个），产物自动上传 Release 页面，分发链接直接给用户。跨平台编译这个事，本地做不了——你一台 Windows 机器编不出 macOS 的包，一台 Mac 也编不出 Windows 的包。

多平台数量越多，云端的优势越明显。需要 Windows 包时本地 30 秒最快，但需要三个平台时云端一次跑完反而更省事，你不用在三台机器上各跑一遍本地打包。

一个提醒：私密项目的边界

PakePlus 创建项目时在你自己的 GitHub 账号下 fork 模板仓库，这个仓库只有你能读写——PakePlus 作者看不到。这意味着你可以放心把项目设成私密，不用担心被别人偷看。但 fork 仓库这个动作本身，PakePlus 客户端是通过你的 GitHub Token 完成的，所以 Token 至少要有 repo scope 的权限。不想给 workflow scope 也行——在 GitHub 设置里把生成的 token 权限调小到只读 repo、去掉不必要的 scope，一样能正常用。

还有个细节：Token 别忘设过期时间。GitHub 现在默认给 90 天过期，过期自动失效，就算有人拿到也用不了多久。每 3 到 6 个月轮换一次，比等泄露了再补救强。

收尾

PakePlus 把"网页套壳"这件事做薄了——薄到你可能以为它只有那个表面的功能。但往深了翻，窗口模式的隐形开关、Token 的分层存储、绿色版的系统旁路、两条打包路径的节奏配合，这些藏得真深的细节才是让它好用的原因。把它用透不只是点对按钮，还得知道每个按钮背后还有什么能调的东西。

我这套资料在GitHub主仓库之外，也同步到了Gitee和GitCode，国内网络访问哪个快就用哪个。
