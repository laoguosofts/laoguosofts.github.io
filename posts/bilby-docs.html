每周追 20 个技术 UP 主，我用 Bilby 搭了一条不被算法打断的追更流水线

2026-10-17 ·约 7 分钟 ·掌柜 老郭

从官方 B 站客户端被推荐流反复带跑偏，到只用 Bilby 做订阅入口、配合飞书笔记和网盘管理学习素材，拆解我花两周磨合出来的一套追更不翻车的实际流程。

旧流程的痛点不在"功能少"，而在"每次都要和自己的注意力打仗"

我现在关注的 B 站技术类 UP 主有 23 个，每周大约有 12~15 条更新。半年前我全部用官方客户端追，流程大概是这样的：

打开 App → 被开屏广告和首页推荐流晃一眼 → 刷到一个看起来有意思的推荐视频，点进去 → 刷了三条发现和本周要学的东西没关系 → 关掉，往下滑找到"关注"二级 Tab → 逐条看更新 → 想看后台听歌写代码时，锁屏后经常被系统省电机制干掉音频 → 想记笔记还得切到飞书 → 来回切换两三次就忘了刚才看到哪 → 一周下来真正看完的不到一半，剩下的要么过期要么被新的挤掉。

这条流程里我至少有三分之一的时间消耗在和推荐流搏斗、和后台保活搏斗、和应用切换搏斗上。不是官方客户端功能不行——直播、充值、投稿、商城，它全有——而是我并不需要这些，它们却每次都挡在我追更的必经之路上。

新流程把 Bilby 插在了"最该纯粹"的那一环

替换方案我花了两周磨合，核心思路是把官方客户端里我真正需要的那一小块——"追关注的 UP 主"——单独抽出来用 Bilby官网 做，其他功能该在哪还在哪。现在我的每周追更流程是这样的：

周一早上自动刷新订阅流 → Bilby 里只有那 23 个 UP 主 → 逐条标记"本周必看"和"有空再看" → 必看的当天用后台音频模式听完/看完 → 看完后统一批量进飞书笔记写一条要点 → 需要反复看的教程从 Bilby 下载到手机本地 → 每晚睡前手动把下载的教程传去夸克网盘归档。

整条流水线里 Bilby 扮演的角色只有一个：纯粹的订阅追更入口。它不负责发现新内容（那还是官方客户端推荐流的强项），不负责做笔记（飞书笔记干这个），不负责归档（网盘干这个），就一件事——让我在一个完全干净的环境里只看我已经决定要看的人。

衔接点一：从官方同步关注清单——一次扫码就能搞定全部

第一次从 官方下载 装上 Bilby 时我最担心的是关注列表要重新手动搜一遍。实际操作比预想的简单：打开 App 直接弹出二维码，用手机上的哔哩哔哩官方客户端扫一扫确认，你在官方客户端里已经关注的所有 UP 主自动同步过来。

这个衔接点是整个流程的地基——它意味着我不需要花一个晚上重新搜 23 个 UP 主。扫码、等 3 秒、首页直接就有内容了。如果遇到同步没生效的情况（我只遇到过一次），退出去重登一次就行，不用做别的。

衔接点二：后台音频保活——这是整个流程最容易断链的环节

技术教程类视频我经常是开着后台音频模式，一边写代码一边听。官方客户端在我这台三年前的安卓机上锁屏后大概有三分之一概率会被系统省电机制干掉，音频突然断了得手动再点开继续，体验很差。

Bilby 的做法是给了一个明确的"音频后台保活"开关，同时 Bilby文档 里给出了系统层面的放行建议：电池设置里把 Bilby 加进无限制后台，关闭多任务一键清理对它的作用范围。我照着设完之后，锁屏续听就没有再断过。这一步看似是小设置，但它是我敢放心把 Bilby 放进每日工作流的前提——后台一断，整条学习链就跟着断。

衔接点三：合集不拆散——省了在搜索结果里翻找的功夫

我关注的几个 Python 和 Rust 教程 UP 主都是按合集更的。官方客户端搜索合集中的某一集时，有时会把合集里的其他单集和合集条目混在一起展示，我得手动识别哪些是同一个合集里的。Bilby 的搜索引擎会把合集当成一个独立实体——搜到某集时，整个合集会作为一个条目展示，点开才看到全部集数；直接搜合集标题时优先展示合集条目。

这个差异在找系列教程时体感差距很大：以前搜"Python 入门"，结果里可能混着合集条目、单集、不同 UP 主的教程，得花几秒过滤；现在搜完一眼就能看到完整合集，点进去一集一集顺着看就行。对经常追系列教程的人来说，这个细节直接决定了搜索的效率上限。

衔接点四：下载 → 网盘归档 → 笔记——三步走不打断

有些教程我需要反复看，比如上周看的那个 Rust 所有权系统的合集。流程是：在 Bilby 里点开合集 → 长按下载 → 晚上睡前把手机里的下载文件夹整个丢进夸克网盘对应分类 → 第二天在飞书笔记里补一条"Rust 所有权系统核心要点"。

这三步之间 Bilby 只管第一步——下载到本地。归档和笔记是后面的事，我不会在看视频的时候同时干这些。这样做的好处是追更阶段完全不被干扰，所有后续处理集中在一个时间块里批量完成。如果在看每一集的时候都停下来记笔记、传网盘，那才是真的打断学习节奏。

效果和边界：省了多少事，什么时候这套流程不划算

跑了一个月，我实际测到的数据：

  • 每周花在追更上的有效时间从 8~10 小时降到了 4~5 小时——少了两次手动复制（把推荐流里点歪的时间算进去），少了后台断流后重新定位的时间
  • 每周看完的视频从 6~8 条涨到了 12~14 条——因为没有被推荐流带走的干扰，每条都看完了
  • 被打断的次数从每天 2~3 次降到了几乎为零——开屏广告没了，推送没了，连开屏倒计时那几秒都省了

但这套流程也有它的边界。三个场景下我还是会切回官方客户端：想发现新 UP 主时（Bilby 不做"猜你喜欢"，想拓展关注清单还是得靠官方推荐流）、想发弹幕互动时（Bilby 支持发弹幕但我习惯在官方客户端发，手感不一样）、需要看直播或充值大会员时（这些功能 Bilby 根本不做）。

本质上这不是"用 Bilby 替换官方客户端"的故事，而是用两个客户端各干自己最该干的事的故事。Bilby 从一开始就没打算成为另一个官方——它的目标用户就是那些已经有了自己的关注清单、不想再被算法牵着走的订阅党。对这类人来说，7.45M 的轻量安装包、只装订阅流的极简首页、零商业化模块，这些"减法"恰恰就是他们要的东西。

想看什么自己搜、自己关注，节奏由你定——这是它产品文档里反复出现的一句话，也是我把它嵌进工作流的核心理由。当我把所有干扰因素从追更环节剥离出去之后，剩下的就真的只是追更本身了。

这类实用工具我习惯在多个仓库留备份，GitHub、Gitee 和 GitCode 各有一份，北方网络不好时直接走 Gitee 镜像就行。
